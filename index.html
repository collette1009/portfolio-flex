배송 VOC 패턴에서는 UX 구조 문제를 재정의해 개발팀에 직접 제안했고, 당일 구현까지 이끌었습니다. 그 결과 반복 CS 인입은 0건 수준으로 줄었습니다. 자유 텍스트에 묻혀 있던 환불·교환 의도는 필수 선택값으로 구조화해, AS 재확인 왕복을 95% 이상 줄였습니다.

HR·노무 도메인이 처음이라는 것을 알고 있습니다. 하지만 저는 새로운 도메인 앞에서 멈추지 않습니다. 택배 표준약관과 물류 계약서도 처음이었지만, Claude로 쟁점을 정리하고 NotebookLM으로 원문을 교차 확인해 정산·배상 판단 근거를 만들었습니다. CS 판단 기준이 없던 환경에서는 처리 기준과 에스컬레이션 구조를 직접 설계해 유관 리더와 협의를 거쳐 공통 운영 기준으로 정리했습니다.

어려운 지식을 빠르게 파악해 고객이 이해할 수 있는 언어로 바꾸는 것. 그것이 제가 새로운 도메인에 들어가는 방식입니다.

Case 01

배송 제약 VOC를 UX 스펙으로 전환 — 개발팀 제안·당일 구현

문제 상황

배송 제약 상품(특정 요일에만 도착)이 장바구니에서 일반 품절 상품과 동일하게 표시되고 있었습니다. 고객은 "왜 주문이 안 되냐"는 문의를 일 6~10건 반복했고, CS팀은 매번 같은 설명을 했습니다.

단순 안내 추가로 해결되는 문제가 아니었습니다. 품절과 배송일 제약을 시각적으로 구분하지 못하는 UX 구조 자체가 원인이었습니다.

01 VOC 패턴에서 UX 구조 문제 재정의

건별 응대가 아니라 반복 패턴을 분석해 이건 CS 응대 문제가 아니라 장바구니 UX 구조 문제라고 재정의했습니다. 시스템에서 품절과 배송일 제약을 구분 가능한지부터 개발 담당자에게 확인했습니다.

02 MVP 스펙·예시 문구까지 직접 설계

단순 보고가 아니라, 구체적인 UX 솔루션 방향과 예시 문구까지 직접 작성해서 개발팀에 제안했습니다.

→ Direct Proposal to Dev Team
제안 "시스템에서 품절과 배송일 제약을 구분할 수 있다면, 장바구니 상품 옆에 문구만 다르게 표시하는 MVP가 가능할까요?"
03 제안 즉시 수용 → 당일 구현 → 유사 케이스로 확장

제안은 즉시 수용되어 당일 구현됐습니다. 관련 문의는 0건 수준이 됐습니다. 이 subtext 구조는 이후 유사한 안내 케이스에도 적용 가능한 기준으로 확장됐습니다.

일 6~10건 → 0건 수준 · 유사 케이스로 확장 적용
UX 스펙 직접 설계 → 개발팀 수용 → 당일 구현 → 유사 안내 케이스로 확장. CS 영역을 넘어 Product 사고로 제품 개선에 직접 기여한 사례.
Case 02

고객 직접 응대 · 400여 개 제휴사 운영 기준 재정비 · Knowledge Base 구축

문제 상황

예약·변경·취소 기준이 제휴 골프장마다 달라 동일 유형 문의에도 상담 기준이 흔들렸습니다. 같은 케이스를 두 사람이 다르게 응대하는 일이 반복됐고, 파트너와의 컴플레인도 구조적으로 발생했습니다.

가장 큰 문제는 파트너 본인도 정책을 깔끔하게 정리해두지 않은 경우가 많아, CS팀과 파트너 양쪽 모두 같은 문의에 시간을 쓰고 있었다는 점입니다.

01 고객 직접 응대 + 400곳 정책 전수 정리

플랫폼으로 접수된 예약·변경·취소·위약 문의를 어드민에서 직접 처리하면서, 동시에 400여 개 제휴 골프장의 위약·취소·동반자 변경 기준을 전수 정리했습니다. 흩어져 있던 정책을 표준 기준으로 통일했습니다.

02 반복 문의 패턴 기준화 · 단일 판단 체계 수립

VOC 분석을 기반으로 반복 문의 패턴을 기준화했습니다. 어느 골프장 문의가 들어와도 상담자가 동일한 기준으로 판단할 수 있는 단일 판단 체계를 만들었습니다.

03 Knowledge Base 구조 + 신규 인력 온보딩 가이드

표준화된 정책을 Knowledge Base 구조로 정리해 파트너가 직접 참조할 수 있도록 했고, 신규 인력도 동일 기준으로 응대할 수 있는 온보딩 가이드까지 함께 정비했습니다. 담당자 교체에도 응대 품질이 유지되는 구조를 확립했습니다.

Case 03

AI로 계약·약관 쟁점 정리 → 원문 교차 확인 · 배상 회수율 14.7배

문제 상황

택배사와 물류 파트너 귀책으로 발생한 사고·손실 이슈에 대해, 접수·증빙·보상·정산 기준이 명확히 분리되지 않은 상태였습니다. 배상은 파트너 관행에 따라 제한적으로 처리됐고, 어떤 기준으로 증빙을 남기고 어떤 항목을 청구할 수 있는지 정리된 적이 없어 손실이 누적되고 있었습니다.

법·계약 영역은 제가 처음 접하는 도메인이었습니다. 하지만 멈추지 않았습니다.

01 Claude로 계약 쟁점 정리

택배 표준약관과 물류 계약서를 Claude로 구조 해석하고, 책임 구간·송하인 통보 의무·접수 기준 등 쟁점을 항목별로 정리했습니다. 흩어져 있던 약관 조항을 운영자가 이해할 수 있는 언어로 재구성했습니다.

02 NotebookLM으로 원문 교차 확인

Claude가 정리한 쟁점을 그대로 믿지 않고, NotebookLM으로 원문을 검색·인용해 교차 검증했습니다. "이 조항이 실제로 존재하는가"를 이중 확인하는 워크플로우입니다. AI 한 곳만 믿지 않습니다.

03 선공제 조항 확인 → 유관 리더 협의·공통 기준 정리

물류 계약서를 다시 검토하는 과정에서 기존 운영에서 활용되지 않던 선공제 조항을 확인했습니다. 사고 유형별 책임 구간과 정산 기준을 직접 설계하고, 유관 리더 보고·협의를 거쳐 공통 정산 기준으로 정리했습니다.

배상 회수율 14.7배 · 월 1,900만 선공제 구조
원문 교차 확인 → 협상 근거 → 공통 정산 기준 정리. 처음 접하는 법·규정 기반 도메인도 같은 방식으로 학습하고, 고객이 이해할 수 있는 운영 기준으로 바꿔냈습니다. HR·노무도 같은 방법론으로 접근합니다.
Case 04

Chrome Extension 직접 구현 → 반복 CS 업무 7→1단계 · 1,151건 처리

문제 상황

대량 취소·반품·재배송 처리 시 동일 항목을 반복 입력해야 했습니다. 처리 건수가 늘어날수록 입력 피로도와 기준값 오입력 가능성이 커졌고, 귀책대상·처리 사유처럼 후속 정산·집계에 연결되는 값은 한 번 잘못 입력되면 운영 데이터 전체가 왜곡될 수 있었습니다.

01 Claude로 Chrome Extension 직접 구현

반복적으로 입력되는 필수값과 기준값을 분리하고, Claude를 활용해 Chrome Extension을 직접 구현했습니다. 재배송·반품 등록 시 주요 항목이 단축키 한 번으로 자동 입력되도록 설계해, 기존 7단계였던 반복 처리 동선을 1단계로 줄였습니다.

02 리스크 구간은 사람에게 남김

모든 단계를 자동화하지는 않았습니다. 귀책 판단·예외 케이스 확인·최종 등록·고객 안내에 영향을 주는 구간은 담당자가 직접 확인하도록 남겼습니다. 자동화의 목적을 단순 속도가 아니라 반복 입력 오류 감소와 기준값 표준화에 두었기 때문입니다.

03 AI 도구 도입 직접 제안 · 업무비 공식 승인

회사 기본 제공 환경 외에도 Claude·GPT 도입 필요성을 직접 기획·제안했고, VOC 분류·자동화 로직 작성·계약 문서 검토·응대 가이드 초안에 목적별로 활용했습니다. 실제 업무 효율화 기여를 인정받아 비개발 직군에서도 AI 도구 업무비를 공식 승인받았습니다. Slack API + Apps Script로 /담당자 슬래시 커맨드 조회 인터페이스를 구축·배포해, 상품 문의 이관 시 매번 엑셀·시스템을 열던 내부 조회 동선도 단축했습니다.

7→1단계 · 1,151건 처리 · AI 업무비 공식 승인
도구를 쓰려고 한 게 아니라 해결해야 할 문제가 있었기 때문입니다. flex에서도 AI를 실제 CX 운영 개선에 붙여본 사람으로 기여하겠습니다.

400여 개 제휴 골프장의 예약·취소·위약·동반자 변경 기준을 전수 정리해 상담 판단 기준을 표준화했습니다.

플렉스의 CX 02

VOC → Product Feedback 루프 — 고객 목소리가 제품 업데이트에 직접 반영되는 구조

VOC 분석 제품 개선 제안 데이터 기반
— 나의 경험

배송 제약 UX 스펙 직접 설계 → 개발팀 제안·당일 구현·반복 문의 0건 수준 / 환불·교환 입력 구조화 → AS 재확인 왕복 95%+ 감소

배송 제약 상품 VOC 반복 패턴을 발견하고, 단순 안내가 아니라 장바구니 내 상품별 subtext로 주문 불가 사유를 안내하는 UX 스펙을 직접 설계했습니다.

개발팀에 MVP 개선안을 제안해 당일 구현까지 이끌었고, 일 6~10건 반복되던 관련 문의를 0건 수준으로 줄였습니다.

자유 텍스트에 묻혀 있던 환불·교환 의도를 필수 선택값으로 구조화해 AS 재확인 왕복을 95% 이상 줄이고, 처리 리드타임을 단축했습니다.

플렉스의 CX 03

인사·노무 도메인 지식 — 복잡한 기준을 고객이 이해하는 언어로 번역

도메인 전문화 지식 번역 Knowledge Base
— 나의 경험

처음 접한 도메인도 직접 학습해 운영 기준으로 바꿔왔습니다

택배 표준약관과 물류 계약서는 Claude로 쟁점을 정리하고, NotebookLM으로 원문을 교차 확인해 책임 기준과 정산 근거를 정리했습니다.

CS 판단 기준이 없던 환경에서 처리 기준과 에스컬레이션 구조를 직접 설계하고, 유관 리더와 협의해 팀 공통 기준으로 정리했습니다.

HR·노무 도메인도 같은 방식으로 접근하겠습니다. 먼저 기준을 이해하고, 고객이 이해할 수 있는 언어로 번역하겠습니다.
